# EasyPub Development Notes

EasyPub is a desktop-only Obsidian plugin that generates platform-specific publishing drafts for Hexo, Zhihu, WeChat Official Account, and Xiaohongshu.

User-facing behavior belongs in [README.md](README.md) and [docs/](docs/README.md). This file records implementation structure and invariants.

## Architecture

```text
main.ts                 Plugin lifecycle, commands, publish orchestration, file IO
settings.ts             Obsidian settings UI
types.ts                Settings, platform, metadata, asset, and PicGo types
modals/DiffModal.ts     Update diff and confirmation
utils/frontMatter.ts    Front Matter parsing and merge rules
utils/platforms.ts      Platform paths, child references, target selection
utils/linkUtils.ts      Hexo URL calculation
utils/hexoCommands.ts   Local Hexo validation, build, and deploy
utils/controlRoom.ts    Blog Control Room discovery and session validation
utils/imageEmbeds.ts    Code-safe Obsidian image embed conversion
utils/picgo.ts          PicGo Server request and response validation
utils/settings.ts       Settings validation and publish configuration fingerprint
utils/async.ts          Bounded waits for external requests

utils/publishSafety.ts  Target conflict checks and Control Room metadata
views/WechatView.ts     Pinned local-draft workbench, crop UI and stale-preview guards
utils/wechat*.ts        Isolated WeChat markdown, rendering, images, API, state and sync
tests/                  Core behavior tests
release/                Manual-install artifacts generated by the build
```

## Publish Model

- Publishing starts from the active Obsidian file.
- WeChat is the exception after initial draft creation: existing local drafts open without source merging. Only the explicit source-refresh command replaces their body after diff confirmation. Sync reads the pinned local draft only.
- WeChat bypasses global PicGo, uses its own settings/cache, and is excluded from other platforms' publish fingerprints. Source settings never overwrite a local draft's `wechat` metadata.
- `pub_id` is the stable identity across source and published files.
- Source identity scanning uses a session-only read-derived index. Vault events invalidate entries; matching IDs are always re-read. Never persist the index or use stale metadata cache to rule out identity conflicts.
- Before reusing a publish target, validate its source ownership and duplicate source IDs. Do not migrate legacy IDs or require new metadata: missing/stale source links remain usable when no competing source claim exists. See docs/review-followup.md for limits and deferred concurrency work.
- Source files keep `子文件`; published files keep `source_file`.
- Existing targets are found by `pub_id`, not filename.
- Unrelated same-name targets are never overwritten; choose a numbered filename.
- Updates pass through `DiffModal` before target writes or external PicGo uploads.
- Recheck source text, source path, and publish settings before uploads and target writes. A failed modal render releases the confirmation lock.
- Network waits are bounded: PicGo heartbeat 10 seconds, uploads 60 seconds, Control Room probe 5 seconds. Late upload responses never resume a timed-out publication; the remote server may still complete the upload.
- Invalid persisted settings fall back to safe defaults; loading never automatically overwrites saved data. Failure to open the editor after saving is reported separately from publication failure.

## Storage Boundaries

- Hexo is outside the Vault at `{hexoRepoPath}/source/_posts`; use Node `fs`.
- Zhihu, WeChat, and Xiaohongshu are inside `{publishBasePath}`; use Obsidian Vault APIs.
- Use `app.fileManager.processFrontMatter` for Vault source metadata.
- Vault-internal `子文件` entries are wiki links; Hexo entries are plain external paths.
- Create Vault folders through `app.vault.createFolder`; create external directories with recursive `fs.mkdir`.

## Front Matter Invariants

- Source-owned fields override matching fields in published files.
- Preserve platform-only fields and the original published `date`.
- Accept data-only YAML/JSON Front Matter; reject executable JavaScript engines, including while scanning other articles.
- Recompute `pub_id`, `source_file`, and `updated`; refresh Hexo `publish_url` when it can be resolved, otherwise preserve the existing value.
- Do not add published-only fields such as `source_file`, `publish_url`, `date`, or `updated` to the source. Remove existing `source_file`, `publish_url`, and `updated` during source metadata updates; preserve a source-owned `date`.
- If source metadata update fails after writing a target, retain newly created targets. Restore existing targets only through guarded writes; report both the original and recovery errors with the target path if recovery fails. Never delete a newly created target during rollback.

## Hexo Invariants

- Resolve the Hexo CLI from the blog repository's local dependencies; never use an `npx` fallback.
- Use Node `createRequire` rooted in the blog repository rather than Obsidian's `require.resolve` shim. Inside Electron, run installed `node` from PATH; packaged Obsidian may disable `ELECTRON_RUN_AS_NODE`.
- Validate the absolute repository path and `_config.yml` before build.
- Parse the complete YAML configuration before `clean`; deployment requires a nonempty string `type` in every configured deploy entry.
- Validate `deploy.type` before deployment.
- Build runs `clean` then `generate --bail`; deploy adds `deploy`.
- Each Hexo command has a 10-minute timeout and non-interactive Git auth.
- `autoDeploy` applies only to Hexo and defaults to `false`.
- Refresh the active article's `publish_url` after successful generation or deployment.

For compatible Blog Control Room repositories:

- Discovery requires an absolute path, `ManageBlog.bat`, `admin/server.js`, and exact `scripts.gui`.
- Reused sessions must be loopback HTTP URLs with one valid token and a successful `/api/status` probe.
- Deploy commands and `autoDeploy` open the protected management flow instead of calling Hexo deploy.

## Image Invariants

- Default Hexo image copies live under `source/picture/easy-pub/{pub_id}` with path and content hashes in filenames. Existing assets are immutable.
- Revalidate attachments and target content after confirmation; a changed or moved target requires a new publication attempt.
- Search both `_posts` and `_drafts` recursively by `pub_id`; updates keep the current directory and draft/pending state.
- Compatible Control Room repositories receive required title/categories/tags and a unique four-digit hex `abbrlink`; plaintext `password` is rejected.
- Write target Markdown atomically. On failure, restore existing content only if it is still the version this operation wrote. Once a target has been written, retain new assets even if recovery succeeds; before target write, clean assets only if no post or draft references them.
- Preserve source attachments, note embeds, and examples inside fenced or inline code.
- PicGo uploads occur only after publish confirmation.
- Cache PicGo URLs by attachment path and content hash.
- Revalidate cached PicGo attachments too; use distinct replacement tokens for different paths with identical image contents.
- Do not read image-host credentials from PicGo configuration.
- Optional PicGo Server Secret is stored in local Obsidian plugin data and sent as a Bearer token.

## Development

### WeChat invariants

- Native Markdown rendering is normalized once for both preview and submission. All workbench CSS is scoped. Stale render generations are discarded; changes during a render queue another refresh.
- Body images use uploadimg (JPG/PNG <1 MB); permanent image material is used for covers (<10 MB). GIF is rejected with an explicit replacement message, never silently flattened. Original attachments and local Markdown body are preserved.
- Cover crop uses current `cover_info.crop_percent_list` with independent 2.35:1 and 1:1 coordinates.
- Account, purpose and processed hash scope material caches. Recheck cached cover existence and local originals; uploads are deferred until sync.
- AppSecret is system-encrypted or session-only; tokens are memory-only. Never log network errors containing credentials.
- Persist uncertain write state BEFORE creating/updating a remote draft. Explicit rejection clears it; transport ambiguity/readback failure retains it for manual recovery. Remote conflict defaults to cancel and is rechecked after uploads.
- `npm run test:wechat-ui` uses installed Chromium and Obsidian API fixtures; it does not substitute for real Obsidian/account acceptance. See docs/wechat.md for verification limits.
- `npm run test:wechat-native` uses a running Obsidian CLI and an in-memory temporary plugin to check native rendering, image decoding and system encryption, without Vault writes or WeChat requests. See docs/wechat-acceptance.md for outstanding account and minimum-version checks.

```bash
npm ci
npm test
npm run check
npm run build
```

`npm run build` runs TypeScript checking, creates the production bundle, and synchronizes `main.js`, `manifest.json`, and `styles.css` into `release/`.

After source or manifest changes:

1. Run `npm test`.
2. Run `npm run build`.
3. Confirm root and `release/` artifacts are synchronized.

## Release

- `manifest.json` is the source of truth for plugin version and minimum Obsidian version.
- Keep `isDesktopOnly: true` while Node/Electron APIs are required.
- GitHub Releases must attach `main.js`, `manifest.json`, and `styles.css` from the same build.
- Do not commit `node_modules/` or local assistant/tooling directories.
